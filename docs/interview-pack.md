## 一、一页纸简介

**TaskForge 是一个权限受控、可恢复、诚实披露的通用 Agent 运行时，附一个企业四角色审查工作流。**

一句话核心立场：**模型只提出 `ToolRequest`，宿主负责权限、校验、执行、幂等、checkpoint——模型从来不是授权系统。**

### 能力骨架
| 层 | 做了什么 | 证据 |
|---|---|---|
| AgentRuntime | 工具提案 → 宿主策略/审批/幂等回执/断点续跑，全部持久化 | 审批暂停可跨进程恢复、重启不重复执行 |
| Provider 中立 | OpenAI Responses + DeepSeek Chat Completions 两个适配器 | 真实 DeepSeek 原生 tool calling 跑通 |
| 企业审查 | 受理→合规→风险→决策固定 DAG，模型只产出 `model_untrusted` 建议，人工最终拍板 | 证据/事实验证（`authority=tool` 一次性回执）+ 跨角色 handoff |
| RAG 评测 | BM25 / dense / rerank 三档消融，真实数据集锁定切分 | TAT-QA + MultiHop-RAG 各 100 例 |
| 诚实工程 | `provider_configured ≠ live_smoke ≠ business_e2e` 分层披露 | 不推断、不伪装，验证记录带签名入库 |

### 三个能打动面试官的证据点
1. **模型无授权 + 宿主执行**：不是"套聊天页"，是生产级 LLM 系统的架构立场。
2. **真实跑过**：DeepSeek 四角色审查链真实完成，留下 verified facts + handoffs；RAG 在真实数据集上出数字。
3. **诚实分层**：演示不伪装成 LLM；`degraded_nonsemantic` 明确标注；live smoke 有签名记录才披露 True。

### 技术栈
Python 3.11 / FastAPI / pydantic(严格模型) / sqlite3 / Qdrant(local) / fastembed(BGE) / Vue3 / DeepSeek / GitHub Actions(ruff + pytest + 前端构建)

## 二、面试问答稿

### Q1：用 30 秒介绍这个项目
"我做了一个权限受控、可恢复的通用 Agent 运行时。核心设计是**模型只提出工具调用方案，由宿主做权限校验、执行、幂等和持久化**——所以模型从来不是授权系统。在这个基础上，我实现了一个企业四角色审查工作流：每个角色跑在同一个运行时上，产出的事实由宿主做证据验证（签发一次性回执），跨角色通过 handoff 传递，最终只有人类能拍板。它已经用真实 DeepSeek 模型完整跑通过，也有真实数据集的检索评测。全程是诚实工程：能验证什么、不能验证什么，API 里都如实披露。"

### Q2：为什么模型只能"提方案"、不能直接执行？
"这是我对 LLM 系统安全的核心认知。如果你把工具直接交给模型，等于把授权交给了模型——一个 prompt injection 就能让它执行不该执行的动作。所以我把边界画在 `ToolRequest`：模型只是提议，宿主做四件事——**能力白名单、参数校验、策略审批、幂等回执**。每一步都持久化，断电重启不会重复执行工具。这不是加一层过滤，是架构立场：可验证地保证'模型无授权'。"

### Q3：最难/最有意思的部分？
"最有意思的是**证据验证 + 诚实披露**。审查链里每个角色产出 claim，宿主验证「该 claim 引用的证据是否真的来自这个角色本次的检索回执」，通过才签发 `authority=tool` 的一次性回执并变成 verified fact；没引到真实检索的保持 proposed。下游角色通过 handoff 拿到这些 verified fact IDs。这套机制让'模型说了什么'和'宿主验证了什么'严格分离。
做真实模型联调时还暴露了几个教科书级问题：决策角色会引用 handoff 的 `fact:<id>`（原来会被严格 gate 拒绝）、模型会编造不存在的证据标签 `K1`、30 秒超时对长输出角色不够。这些都是在真实跑、真实失败中修的，而且都补了测试。"

### Q4：你怎么知道它真的能用？——四层披露
"我的答案是**不靠感觉，靠分层披露**。API 里四个字段各自独立，互相不推断：
- `provider_configured`：只表示参数齐全；
- `contract_tested_mock`：模拟 HTTP 契约测试通过；
- `live_smoke_verified`：有一条**签名验证记录**，只有真实跑过 `--confirm-live-call` 的冒烟、成功后才写入，绑定 provider/model/run_id，篡改即失效；
- `business_e2e_verified`：业务端到端的持久化验证记录。

所以配置了 key ≠ 验证过，跑过一次 ≠ 稳定。我不从环境变量或 API key 推断任何成功。"

### Q5：RAG 那部分数字说明了什么？
"我在两个真实数据集上做三档消融（BM25 词法 / dense 向量 / +rerank），各 100 例锁定切分：
- **MultiHop-RAG**（真实新闻跨文档）：BM25 recall@10 = 0.858，dense = 0.597
- **TAT-QA**（金融表格+文本）：BM25 = 0.658，dense = 0.543（rerank 0.583）

关键：接入真实语义 Embedding（BGE-small）后，dense 档从 0.056 涨到 0.597——**10 倍提升**。这也展示了我的诚实：早期 dense 用的是非语义 hash 向量，我明确标注 `degraded_nonsemantic`，不拿假 dense 的数字冒充成绩。BM25 还略高是因为目前是每文档一个向量、长文被截断；下一步做文档分块，dense 有望反超。"

### Q6：真实模型联调遇到什么问题？
"三件事，都是真实跑出来的：
1. **引用契约**：决策角色引用 handoff 共享事实时写 `fact:<id>`，原来的严格 gate 只认检索回执——我改成接受宿主创建的共享事实，同时仍然拒绝编造的引用；
2. **编造证据标签**：模型会自造 `K1` 这种标签当引用——我在评审指令里明确'只准引用检索到的确切 evidence_id/source 或 fact:<id>'；
3. **超时**：30s 对长输出角色不够，调到 120s。
每条都补了测试。这反而成了加分项——说明我的验证逻辑是真实在抓错的，不是摆设。"

### Q7：和 LangChain / LangSmith 之类比，你为什么要自己写？
"LangChain 是帮你把功能串起来的框架，LangSmith 是可观测平台。TaskForge 不是要替代它们，而是做一个**教学级的最小完整实现**：核心 Agent 循环、权限、幂等、checkpoint、证据验证、诚实披露，每一层都可读、可测试、可扩展。自己写一遍才能真正理解'模型无授权 + 宿主执行'意味着什么。作为作品，它的价值在于架构决策和诚实工程，而不在于功能数量。如果要做生产部署，我可以在保留架构的前提下接 LangSmith 这类观测层。"

### Q8：下一步你会做什么？
"按优先级：
1. **文档分块 + 真实 reranker**——让 dense 检索在长文档上反超 BM25，补齐 RAG 故事；
2. **业务 E2E 的持久化验证**——把'真实跑过四角色链'也做成签名记录，让 `business_e2e_verified` 诚实变 true；
3. **产品化审查工作流**——把前端工作台打磨成可给真实用户用的审查控制台，而不是演示。
（注：1、2 其实已经在做/做了——语义 Embedding 已接入，验证记录机制已上线，见仓库历史。）"

### Q9：技术选型为什么？
- **pydantic 严格模型 + sqlite**：所有运行时状态都是强校验、可序列化的，断点续跑安全；sqlite 单机够用、零运维。
- **Qdrant local**：真实向量索引（named vectors + RRF）但不引入外部服务依赖。
- **DeepSeek Chat Completions**：OpenAI 兼容，写了一个通用 Chat Completions 适配器（无状态续接，靠 checkpoint 重建完整消息历史），换 provider 只改配置。
- **Vue3 + Vite**：轻量工作台，类型安全（vue-tsc 在 CI 里强制）。

### Q10：项目有什么诚实的局限？
"有三点我不回避：
1. **没有真实用户/部署**：它是能力样本，不是被业务使用的产品；
2. **长文档 dense 被截断**：目前每文档一个向量，长文只嵌入前 512 token，这是 BM25 还略高的主因；
3. **严格协议对真实模型有抖动**：四角色链真实跑通过，但个别环节可能因模型不守引用契约而失败，需要重试或提示约束——这本身就是'模型不可信'假设的体现。"
